# Compatibility and deprecation policy

Status: **pre-1.0 release candidate.** Nothing below is a promise to external integrators yet; it is the rule the project holds itself to so that a hospital's stored data and a deployed instance survive upgrades.

## Deprecation policy
1. **API.** Routes live under `/api/v1`. A breaking change (removed or renamed field, changed meaning, new required field) requires a new prefix or an additive, defaulted field; the previous behaviour is kept for at least one release candidate after the replacement ships and is announced in `CHANGELOG.md` under "Deprecated". The committed `docs/api/openapi.json` and `packages/contracts/ts/types.ts` are regenerated by `scripts/export_openapi.py` and `packages/contracts/generate_ts.py`; CI fails if they drift from the running app.
2. **Authorization policy.** A new route must have an entry in the policy table or CI fails (`tests/security`).
3. **Data.** Database changes ship as Alembic migrations with a working downgrade. Stored rows are never reinterpreted: the audit-hash scheme is versioned and old schemes stay verifiable (ADR-0020, `tests/resilience/test_audit_hash_compat.py`).
4. **Backups.** A backup written by any released candidate must restore with the current `scripts/backup_restore.py` (old-format package tested in `tests/resilience/test_audit_hash_compat.py`).
5. **Model artifacts.** Exchange formats are safetensors/JSON only (no pickle). A model format change needs an ADR and a parity test against the previous artifact.
6. **Research modules** (labelled in the UI/API, e.g. CP-SAT) carry no compatibility promise.

## What is *not* covered
Real partner deployments do not exist yet; no upgrade path has been exercised on hospital data.
